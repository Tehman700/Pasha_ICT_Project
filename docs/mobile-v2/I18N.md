# Language and input rules

**The apps are English-only.** Decided with the user on 21 Aug 2026, replacing
the earlier "Urdu is required, not optional" rule. Do not add Urdu to
`apps/mobile-android/`, and do not re-raise it — it was decided deliberately,
after the trade-off was put in front of the user.

The filename stays `I18N.md` because a dozen links across `docs/mobile-v2/`
point at it. What it now documents is the language decision and the input
rules, which are unchanged and still binding.

## Scope of the decision

| Surface | Language |
|---|---|
| `apps/parent-app/`, `apps/staff-app/` (the shipping apps) | **English only** — extended to them 21 Aug 2026 |
| `apps/mobile-android/` (parked) | **English only** |
| `apps/admin-web/` | English + Urdu — **leave alone** |

The decision was first scoped to the native rebuild, then extended to the React
Native apps the same day. The اردو toggle is gone from all six places it
appeared, and the apps' provider pins the locale to `"en"`.

**The `ur` block in `packages/shared/src/i18n/index.ts` stays**, along with
`dir()`. They were deleted at first and that broke admin-web, which is still
bilingual and reads both. Urdu is unreachable *from an app* rather than removed
from under the dashboard.

`t()` keeps its signature so no call site changed, and the `Locale` type is
still exported because `User.locale` is a backend field in
`docs/api/openapi.yaml`. **The API contract is untouched.**

`useLocale()` still returns `locale` and `isRTL` as fixed values, so the ~40
call sites that read them still compile. `toggle` is gone — a control that
does nothing is worse than no control.

**The admin dashboard keeps its Urdu.** Only the apps changed.

### What this costs, recorded honestly

The native apps will ship with less language coverage than the apps they
replace. Guards and drivers are the roles least likely to be comfortable in
English and the ones using the app under time pressure at a gate. The user
weighed this and chose English-only; it is written down here so the decision
stays visible rather than looking like an oversight later.

### What was removed when the decision was made

- The `values-ur/strings.xml` files for the two flavors' launcher labels.
- `core-i18n` as a module — with one language it earns nothing. Strings live in
  `app/src/main/res/values/strings.xml`.
- The Noto Nastaliq Urdu font, the parallel Urdu type ramp, and the in-app
  language toggle from the plan.
- `name_ur` from parent registration. It is `nullable: true` in
  `docs/api/openapi.yaml`, so omitting it needs **no backend change** — the
  contract is untouched.

## Still use string resources

One language does not mean string literals in composables. Keep every
user-visible string in `app/src/main/res/values/strings.xml` and pull it with
`stringResource(R.string.…)`.

The reason is no longer translation. It is that the copy for both apps becomes
reviewable in one file instead of scattered across thirty composables — which
matters when the wording at a school gate has to be unambiguous.

The scaffold does the opposite everywhere; not one string in `screens/` uses
`stringResource()`:

```kotlin
Text(text = "What is your email address?")     // every screen looks like this
Text("Sending your code...")
```

## RTL — removed

`android:supportsRtl` is **`false`**. Right-to-left layout existed only to
serve Urdu, and the user asked for it to go with it (21 Aug 2026). The app now
stays left-to-right even on a device whose system locale is RTL.

The existing `start`/`end` padding and the two `Icons.AutoMirrored.*` arrows in
`Scaffolding.kt` were left alone. They behave identically to `left`/`right` in
a left-to-right layout, so rewriting them would be churn with no visible
effect — and it keeps the door open if RTL ever comes back.

## Numbers, phones, CNIC

**Western Arabic numerals (0-9)** throughout, for phone numbers, CNIC, times,
and queue positions.

Input rules, enforced at the field layer:

- **Phone: exactly 11 digits, starting `0`.** Hard cap — the field must not
  accept a 12th character. (The scaffold's `PhoneNumberRow` currently does
  `take(15)` with a country-code picker; both need replacing.)
- **CNIC: `38515-1952462-5`.** Dashes inserted automatically as the user types,
  hard-capped at 13 digits. Stored digits-only.

## Backend error strings

Backend `detail` strings are English-only, which now matches the apps, so they
can be shown as-is. Still map the common ones (`401`, `403`, and `409` from
`/trips/start`) to friendlier local copy — a raw server string is a poor thing
to hand a guard mid-handover — and fall back to the server's text for the rest
rather than showing nothing.

## Audit before every build

```bash
# String literals inside composables - should return nothing but previews/tests
grep -rn 'Text(\s*"' apps/mobile-android/app/src --include=*.kt
```

This is a release gate, not a nice-to-have.
