# Urdu and English

**Urdu is required, not optional.** Every user-facing string ships in both
languages *in the same change that introduces it*. This is a root `CLAUDE.md`
constraint and a competition requirement — the market is Pakistani parents,
guards, and teachers, many of whom do not read English comfortably.

## The failure to avoid

The React Native build shipped nine untranslated strings that had to be found
later by grep sweep. They were all added the same way: a screen written in a
hurry with English inline, meaning to come back.

The scaffold has this problem **everywhere** — every composable hardcodes
English:

```kotlin
Text(text = "What is your email address?")     // ← every screen looks like this
Text("Sending your code...")
CoachMark("Know who is around, wherever you are", …)
```

Not one string in `screens/` uses `stringResource()`. Fixing this after the
fact is far more expensive than doing it from the first screen.

## The rule

**No string literal ever reaches a composable.** Every user-visible string is
`stringResource(R.string.…)`, added to `values/strings.xml` and
`values-ur/strings.xml` in the same commit.

A screen is not done until both files have its keys.

## Layout

```
core-i18n/src/main/res/
  values/strings.xml        English — the default
  values-ur/strings.xml     Urdu — must have every key values/ has
```

Android resolves `values-ur/` automatically when the device locale is Urdu, and
per-app locale switching uses `AppCompatDelegate.setApplicationLocales()` (or
`LocaleManager` on API 33+).

## In-app language toggle

The system locale is not enough. A parent with an English phone still needs
Urdu, and the React Native apps put a toggle in the top-right of the welcome
screen. Keep that.

Persist the choice in DataStore, apply it at app start, and send it to the
backend — `User.locale` is `"en"` or `"ur"` and drives server-side content
like announcements and name audio.

## Typography — the part that breaks if rushed

Urdu is Nastaliq, and it does not survive the Latin type ramp:

- **Zero letter-spacing.** The Latin ramp's negative tracking (`-0.8sp` on
  `QuestionStyle`, `-1sp` on `displaySmall`) **severs Nastaliq glyphs**. This
  is not a subtle degradation; it makes the text wrong.
- **Much taller line-height.** Nastaliq's descenders cascade diagonally and
  collide at Latin line-heights. Budget roughly 1.6–1.8× the font size.
- **Its own font.** Ship **Noto Nastaliq Urdu** in `res/font/`. Do not rely on
  a system fallback — coverage on cheap Android handsets in this market is
  exactly where it fails.

Implement as a parallel `Typography` selected by locale, the way the React
Native apps did:

```kotlin
@Composable
fun appTypography(locale: AppLocale): Typography =
    if (locale == AppLocale.UR) UrduTypography else LatinTypography
```

## RTL

`android:supportsRtl="true"` is already set in the scaffold's manifest. Beyond
that:

- Use `start`/`end`, never `left`/`right`, in every padding and alignment.
- Use `Icons.AutoMirrored.*` for directional icons. The scaffold already does
  this for the back/forward arrows — keep it up.
- The `OnboardingScaffold` back/next row mirrors automatically if built with
  `Arrangement` and weights rather than absolute positioning. It currently is.
- **Do not mirror the QR code, the camera preview, or photos.**

Test by switching the app to Urdu, not by forcing RTL layout direction on an
English build — that catches mirroring bugs but misses every font and
line-height problem, which are the ones that actually ship broken.

## Numbers, phones, CNIC

Keep **Western Arabic numerals** (0-9) in both languages for phone numbers,
CNIC, times, and queue positions. Eastern Arabic numerals are correct
typographically but are read less reliably by this user base on a screen, and
they make a phone number harder to check against a physical ID card.

Input rules, enforced at the field layer in both languages:

- **Phone: exactly 11 digits, starting `0`.** Hard cap — the field must not
  accept a 12th character. (The scaffold's `PhoneNumberRow` currently does
  `take(15)` with a country-code picker; both need replacing.)
- **CNIC: `38515-1952462-5`.** Dashes inserted automatically as the user types,
  hard-capped at 13 digits. Stored digits-only.

## What is not translated

- The gate glyph and the wordmark "Rukhsat" — it is already an Urdu word (رخصت).
- Phone numbers, CNIC, timestamps.
- Backend `detail` error strings are English-only. Map the common ones
  (`401`, `403`, `409` from `/trips/start`) to local Urdu strings; fall back to
  the server's English text for the rest rather than showing nothing.

## Audit before every build

Run this sweep before any APK ships, and fix what it finds:

```bash
# String literals inside composables — should return nothing but previews/tests
grep -rn 'Text(\s*"' apps/mobile-android/*/src --include=*.kt

# Keys present in English but missing in Urdu
diff <(grep -o 'name="[^"]*"' core-i18n/src/main/res/values/strings.xml | sort) \
     <(grep -o 'name="[^"]*"' core-i18n/src/main/res/values-ur/strings.xml | sort)
```

The second command returning nothing is a release gate, not a nice-to-have.
